# 工作台已接入清单加载慢诊断

## 结论

主要耗时发生在 AutoFlow 后端的 FOP 对接取数链路：先读取授权范围内完整候选队列、逐单补详情、分页读取客户收款，再在本地按实际付款时间关联、筛选、排序、合计和分页。页面只要 1 条或 50 条，后端仍执行大致相同的全量读取。此次诊断未修改业务实现或 FOP 后台。

## 实测范围与方法

2026-11-10 在本地 AutoFlow 服务、现有 PostgreSQL 与当前 Kingdee 测试环境测量。管理员与 Alex 本人分别通过现有业务服务及实际授权执行只读查询；另用正常管理员登录后的 HTTP 请求复核页面使用的接口。隔离诊断进程只记录操作名、条数、字节数、耗时和错误类型，不保存订单、收款明细或凭据。统计为顺序采样，非压力测试，不是 SLA 或生产 P95。

| 范围与清单 | 本次耗时 | 返回结果 | 测量入口 |
| --- | ---: | --- | --- |
| 管理员待审核，第 1 页 50 条 | 11.27 秒 | total=84，返回50 | 实际 HTTP |
| 管理员待审核，第 2 页 50 条 | 8.37 秒 | total=84，返回34 | 实际 HTTP |
| 管理员待审核，仅请求 1 条 | 12.66 秒 | total=84，返回1 | 服务分层计时，冷启动 |

管理员备货在隔离服务中连续两次分别为4.25秒、4.69秒，第二次仍读取40页收款，证明重复访问并未复用收款结果。首轮待支付错误后仍有3个已发出的详情请求完成，其计时落在下一窗口；备货结论使用独立收款阶段、无重叠的第二次测量和HTTP复核。后续探针已固定每次调用所属记录，防止跨窗口归属。

## 耗时构成和代码位置

1. **待审核逐单补查详情。** 管理员50条请求实际先查84笔列表（0.55秒），再补84次详情（并发4，阶段耗时5.25秒），然后拉40页收款（4.78秒）。业务取数共125次上游调用，另有权限请求。详情单次中位约0.23秒，数量放大后形成明显等待。`backend/src/modules/fop-data/fop-kingdee.provider.ts:530` 的 `readCustomerPaymentPage` 在分页前补齐全部候选详情；`:784` 的 `enrichOrderDetails` 每笔单独请求。
2. **每次重复扫描授权内收款。** `customerPayments`（同文件`:569`）仅按公司参数分页，每页100，先读第一页再每批并发4页；没有按本次订单集合限制或复用完成结果。管理员一次读取3,961条、约12.74MB解码后JSON，个人账号读取140条、约1.01MB。两者都先全读授权内收款，再按公司＋来源类型＋单号关联。管理员备货原始两页仅约0.52～0.66秒，主要等待在这40页收款。
3. **已完成的时间筛选在原始历史扫描之后。** `readSalesCompleted`（同文件`:609`）先串行读取100条/页的原始订单，再读取付款记录并筛选近一周。Alex最终26笔，却先读取47页、4,610笔原始记录（13.96秒、约12.85MB）。范围扩大时成本随历史记录增长。管理员大范围历史查询此前的超限记录不能当成本次新测数据。
4. **列表翻页、排序与自动刷新重复执行重查询。** 备货的 `getStockOrders` 在 `backend/src/modules/fop-data/fop-data.service.ts:1137` 取全量后再筛选切页；履约同样在对接层切页。`frontend/src/views/autoflow/FopOrdersView.vue:355` 与 `StockOrdersView.vue:91` 每30秒刷新，并响应页面重新聚焦、恢复可见及联网；已有加载中保护，不能据此认定每次事件都会并发重复请求。但多页面、多账号以及每次刷新会重复扫描数据。浏览器中止请求未通过控制器传播给FOP扫描，切换页面后的旧任务可能继续运行，此为代码确认的放大风险，尚未进行并发压测。
5. **Dashboard只复用total，不使底层查询变轻。** 缓存缺失时调用同一列表接口pageSize=1，符合此前确认方案；但此次实测仍扫描84笔、补84份详情和40页收款。缓存命中才可避免该调用。问题不能仅靠修改前端数字统计或减小pageSize解决。

上述耗时含网络等待与对接层处理，未做浏览器渲染性能剖析；实际HTTP响应本身已耗时8～11秒，足以确认主要等待在接口侧。权限复验仍保留，管理员本地范围检查合计仅约30毫秒，不是主要瓶颈。并发请求耗时之和不能当成用户等待时长；阶段耗时使用实际墙钟时间。单次FOP请求多数为数百毫秒，当前证据主要指向调用数量与执行顺序，不能据此认定FOP数据库慢SQL。

## 同时发现的失败项

- 管理员待支付本次约8.28秒后失败：已读2页、200笔候选并启动129次详情请求，详情归属／状态一致性校验失败后返回 `fop_permission_denied`。这不是成功查询的正常延迟，具体不一致字段仍需单独核对。
- 管理员待履约本次约0.79秒返回 `fop_result_too_large`，失败来自上游接口；继续等待或增大前端超时不能解决上游容量限制。
- 已完成和待支付／待审核前端允许120秒，备货仍为默认30秒；对接层有60／90秒扫描限时。时间预算不一致有超时后后端继续工作的风险，不能仅把超时调大作为性能修复。

## 建议实施顺序

1. 将客户实际付款时间关联、授权范围、筛选、排序、总数和分页下推到FOP同一个列表接口，保留原业务口径与完整分页。收款数据可提供按授权订单集合批量查询，或在FOP维护可查询的付款时间投影；避免每次扫描完整历史。
2. 列表一次返回必要国家、商品图及展示字段，详情改为批量或仅当前页补充。国家筛选和全局候选项当前依赖详情，不能直接挪到分页后而破坏筛选／统计正确性；须先补齐列表筛选字段。
3. 在对接层按真实身份、公司、组织范围版本和查询条件合并相同在途读取；可评估短时付款索引缓存，保留实时权限复验和范围变化失效。缓存不跨员工授权混用，也不缓存权限来绕过撤权检查。
4. 对自动刷新按数据变化、可见性和最后成功时间节流，传播请求取消；保留手动刷新。先减少重复重查询，再统一合理的端到端时间预算。

当前仅完成诊断，未实施上述性能优化。不能承诺具体优化后耗时，需同口径复测第一／第二页、空结果、筛选、个人／部门范围与异常退出。
