2026-11-11 首轮实施

本轮结论与交付范围

已完成一轮可直接落地的查询优化：履约订单以本单“收款日期”作为客户付款时间，备货清单使用本单收款日期；移除这两类清单对收款单的全量扫描与关联。首页待办缺少前端缓存时，调用原工作台列表接口的轻量计数模式，读取其完整范围 total，跳过订单详情补充。没有新建或调用独立 FOP 统计接口。

0.61 秒管理员待审核计数，84 条，实际 HTTP
5.53 秒 · 下降 51%待审核首屏：原 11.27 秒
0.74 秒 · 下降 85%备货首屏：原 4.86 秒

本轮修改位于 AutoFlow 前端与 BFF 对接层，已在本地服务连接现有 FOP 测试环境复测。已核对 /Library/VSCode/dtr5b 的元数据、支付回写、采购与出库状态工具类。本轮没有改动或部署 FOP Java 生产代码；当前已发布的 employee-orders 自定义网关实现未在该源码库中找到，不能把本地源码存在等同于线上接口已具备能力。

本轮尚未解决全部慢查询：待审核仍有逐笔详情读取；已审核清单仍扫描历史订单；管理员待履约仍返回上游查询超限。以下分别给出已实施结果、字段审查清单与下一步最小改造方案。

已实施的功能与口径修正

时间字段含义补充：源单付款时间（hzkj_datetimefield）是 C 端买家向店铺付款的时间；收款日期（hzkj_receipt_date）是客户向 FOP 付款的时间。两者是不同业务事件，均可由履约订单提供，不能互相替代。近一周等范围仍按此前确认的本单收款日期筛选。本轮接口 consumerPaidAt 作为收款日期兼容别名，其名称不代表 C 端时间；如展示 C 端付款时间，应独立映射源单付款字段。

事项本轮实现一致性要求
履约付款时间hzkj_receipt_date → paidAt → consumerPaidAt。兼容字段 consumerPaidAt 保留供页面、筛选、排序及导出使用；上游排序映射为 paidAt。不取 Shopify 源单付款时间，不回退创建、审核或采购付款时间；缺少本单日期保持未知。
时间范围已有近一周／近一月／近三月筛选统一使用上述本单时间；已完成原始事实直接读取 hzkj_receipt_date。保持 UTC+8 业务时间与现有滚动范围算法；日期筛选在分页和合计之前执行，不截取当前页伪造总数。
取消无必要关联履约待办、销售已完成、备货清单不再调用 queryReceipt，不再每次扫描公司内收款历史。财务回款金额与物流成本分析保持独立事实、授权和原有口径。
首页轻量计数前端继续复用未筛选工作台 total 的 60 秒缓存；缺失时调用原列表 API，增加 BFF 参数 projection=count。轻量路径读取同一 FOP 员工列表第 1 页、1 条；返回 total、items=[]。不调用 FOP_SUMMARY_URL，不补收件信息、商品图或国家候选项。
计数适用边界可由现有上游完整表达的待办范围走轻量路径；本地时间、国家、待审核仓库等尚未下推的筛选仍走完整过滤路径。不为了计数提速忽略筛选；保留角色授权、身份回显、公司白名单、员工范围与查询后范围复验。
待支付默认列表无本地时间筛选时恢复上游真正分页，只补当前页详情；本次实际读取 50 条，不扫描 17,535 条待支付。原有详情归属与状态校验保留；本次成功不代表全部历史异常数据已修复。
导出与演示数据保留待支付／待审核完整清单导出路径；待履约继续按上游固定 ID 清单分批导出。演示付款字段同步为本单收款时间。独立审查发现并修复了大于 100 条导出误入普通分页的回归风险，新增覆盖用例。
经理数据范围延续已实现的“默认个人、自行切换部门、保存入库”机制；计数和列表共用当前范围。范围切换、退出及会话变化清空前端计数缓存；本轮没有另设 Dashboard 权限口径。

单据字段审查：可以直接用本单的部分

“单业务单据”包括其表头、分录，以及 FOP 已维护的回写状态；并不意味着数据库物理上只能读一张表。查询应该以业务主单为授权和分页单位，避免为展示本单已有信息再扫描其他业务单据。基础资料名称、SKU 图片等引用字段可在本单 API 投影中返回，不能因此产生浏览器逐行请求。

字段／业务事实已核对来源本轮处理／接口建议
客户付款时间、付款状态履约 hzkj_receipt_date / hzkj_receipt_status；支付插件回写。本轮已直接使用日期，取消收款单关联。收款状态枚举与备货不同，继续各自解码。
审核状态、取消状态、客户、业务员、金额、币种、仓库本单表头与基础资料引用。继续使用订单 API；不为基本信息扫描采购、发运或收款单。
收件人、国家、地址、商品分录与图片履约 queryOrderDetail/queryOrderList 已提供；当前员工分页投影尚未补齐。目前仍补同一履约单详情，不属于跨业务单据。下一步将必要字段放进员工分页接口，一次返回；国家候选项须覆盖完整授权筛选范围。
采购汇总进度与分录采购进度hzkj_purchase_status / hzkj_entrypurc_status / hzkj_purchase_time；OrderPurchaseStatusUtil 统一回算。本单可供采购阶段展示。不能把“采购中”直接当作“供应商已付款”；完整待采购规则仍需核对付款与下单事实。
齐套hzkj_complete_set；AllocationService 从有效配货事实回写。建议本单字段供列表读取；历史回填、反审核和作废回滚需联调确认。
出库状态、时间与数量hzkj_outbound_status / hzkj_outbound_time / hzkj_delivery_status 及分录 hzkj_outbound_qty；OrderOutboundStatusUtil。优先发布本单投影；不为简单出库进度再扫描出库单。售后链路有独立处理，不能混成主流程出库。
平台履约／推送状态hzkj_fulfillment_status，以及源码中的 hzkj_shopify_push_status、平台履约标识。本单存在候选字段；须确认“平台已发货”与本系统“推送成功”的精确映射、部分与回退情况，再用于队列。
备货日期、备货类型与进度备货单本身的收款日期、类型、订单／审核／采购状态。本轮已取消收款单扫描；列表分页进一步下推属于下一轮。

发现的契约冲突：现有导出接口文档把采购状态描述为 0 未采购、1 采购中、2 已完成；当前 OrderPurchaseStatusUtil 则定义 0 未采购、1 部分采购、2 采购中、3 已入库、4 已发货。应以确认后的部署版本与业务含义发布版本化契约，不直接把 2 映射为采购完成。该差异也是本轮没有自行开启采购队列的原因之一。

剩余跨单据字段：逐项人工确认表

以下是源代码、已发布查询文档及当前对接需求中的剩余关联事项。标记“确需”表示现有本单字段不足以表达所列明细；标记“可消除／待核验”表示有本单回写候选，优先补投影。各项均未在本轮擅自扩张权限或启用新的跨单据查询，决策留待人工逐项确认。

编号与字段为何需要关联／能否消除建议方案人工确认项
C01 供应商付款状态、付款时间、退款后余额采购申请／采购单／付款事实；履约本单采购状态不能证明款项已付清。现有证据不足以消除关联。采购工作台以采购单为主单返回其自身付款事实；履约清单只需进度时由 FOP 回写版本化摘要，不在 BFF 扫全部付款记录。确认主单、部分付款与退款规则；批准本单摘要或当前页批量关联。
C02 采购单号、1688 单号、供应商联系人／旺旺采购关系与供应商资料，可一履约多采购；确需明细关联。首屏只返回已有汇总；展开、催办时按当前页授权来源行批量查，保留独立采购权限。确认首屏必需列及延迟加载列，确认联系人版本。
C03 供应商发货阶段、运单与到货明细分录采购状态已回写发货／入库阶段；具体供应商运单及多次收货仍来自下游。阶段展示优先本单回写；运单与收货细项仅在展开时关联。确认采购分录枚举、虚拟商品、库存供货及退货回滚。
C04 配货单号、是否已创建、配货审核状态订单齐套字段不等价于配货单存在或审核通过；尚无已核实的完整本单投影。优先在订单返回关联 ID 与回写摘要；如确需全部配货单明细，再按当前页 IDs 查询。确认有效配货单、作废／反审核，以及一单多配货的合并规则。
C05 发运单阶段、包裹、物流渠道与末端追踪号本单平台状态不能表达多包裹及各发运单审核、首末端追踪关系；明细确需发运单。待履约是否入队优先本单确认后的回写状态；详细发运信息按当前页关联，避免先扫全部发运单。确认队列依赖的最小状态，确认有效包裹及重复追踪号处理。
C06 拦截发货、取消拦截来源可能在配货／出库流程；未核实履约本单中完整、及时的回写字段。先确定唯一权威字段；能够回写则直接展示。未知不得解释为“取消拦截”。确认字段、更新时机、撤销语义与历史补齐。
C07 售后单号、处理状态、更新时间、换补发信息售后独立生命周期；一个来源订单可有多笔案件，确需售后单。售后工作台以售后单为主查询，返回必要来源订单快照／引用；保留售后与订单授权交集。确认以案件还是履约订单分页，以及多案件合并口径。
C08 采购退货单号、实物退货数量、退款、退货物流退货独立单据，可能一退货多履约；确需关联与来源分摊。按已确认清单单位分页，再批量加载退货明细；不得用采购状态替代实物退货事实。确认实物退货与仅退款边界、主行单位及金额去重。
C09 可用库存／锁定库存／库存台账库存余额来自台账；订单齐套或“有库存”标志不是实时余额，确需独立库存资源。库存工作台直接查询库存台账；履约清单仅展示已回写齐套状态，避免为每单重算余额。确认是否需要首屏实时数量；如需，采用当前页客户＋SKU＋仓库批量读取。
C10 实收金额分析、物流实际成本／成本确认时间收款与发运费用是财务事实；订单日期能替代时间筛选，不能替代实收分录、退款或实际运费。保留财务分析独立 API 与独立权限；本轮清单优化不改账务口径。确认财务指标继续使用既有方案，后续单独优化。

下一轮最小改造方案与实施顺序

前端优先：减少重复请求，保持真实数据口径

优先级方案边界与验收
已完成首页复用工作台 total 缓存；缓存缺失只走同一列表轻量计数。冷进入首页、列表返回首页、个人／部门切换、退出重登分别核对；错误仍显示不可用或未配置。
P1统一列表请求管理：同用户＋范围版本＋完整筛选＋排序＋分页合并在途请求。不以 abort 一个消费者取消其他消费者；旧范围响应不得覆盖新页面。
P1复用最近页面数据；显示更新时间，返回列表先展示有效缓存并后台刷新；手动刷新绕过缓存。短 TTL 与容量限制；保存、审核、组织变化、角色切换、会话重置主动失效。敏感订单内容只在内存，不持久化到浏览器存储。
P1自动刷新按“可见、在线、空闲、距上次成功足够久”触发；聚焦与定时刷新共用节流。优先消除重复刷新，再讨论把 30 秒改为 60 秒；业务时效目标需明确。
P2列表显示必要字段；详细采购、物流、售后信息按展开加载。仅能延迟展示字段，不能延迟决定入队、排序、总数或筛选的事实。

必须补齐的 FOP 能力：先调整现有列表投影和过滤

  1. 最先处理历史扫描。在现有 employee-orders 列表支持“本单收款日期起止＋已审核状态”过滤，并在 FOP 分页前执行；同步确认取消订单在销售已完成中的现有口径。目标是“近一周 26 条”只读该窗口的结果，而非 4,610 条历史。
  2. 补齐同单字段投影。员工分页列表一次返回国家、收件人、必需商品字段；国家候选项由相同授权和筛选条件生成。完成后取消当前 84 次同单详情请求。不另建跨单据汇总服务。
  3. 修复待履约超限。先按已确认的本单支付／平台推送状态筛选主单，再分页主单 ID；详细发运信息仅加载本页。先核对本单回写覆盖率，必要关联按 C05 人工确认。不能仅调大扫描上限。
  4. 备货真分页。将已支持的类型、状态、业务员、时间范围和排序下推到备货主单；返回完整范围 total。当前 151 条可以快速返回，但不能让增长后的历史量继续在 BFF 全读。
  5. 轻量计数可进一步下沉。目前 BFF 用同一 FOP 列表的 pageSize=1 取 total；FOP 仍可能计算该接口约定的金额合计。后续可在同一个接口增加明确的 count 投影，只计算主单总数，并版本化响应字段；无需独立统计 API。

推荐的统一查询执行顺序

当前账号认证与授权 ∩ 当前本地个人/部门范围
  → 同一主单上的状态、收款日期、搜索、仓库/国家过滤
  → 稳定排序（收款日期 + 唯一主键；空日期末尾）
  → 同一过滤条件计算主单 total，并分页主单 IDs
  → 批量读取本页主单表头与完整分录
  → 仅对人工确认的必要字段，批量补本页下游信息
  → 返回 items / total / page / pageSize / 范围版本
  → BFF 复验范围 → 前端展示与缓存

主单分页不能被分录 join 放大；SKU 搜索应先找命中的主单 ID，再返回该订单全部商品。total 是主单数，不是分录数。筛选、分页、合计、导出必须使用同一谓词和空值规则。列表默认每页 50；当前网关单次上限 100 是本项目契约，不能当作苍穹所有 OpenAPI 的统一平台上限。

苍穹操作 API 的可用过滤参数、数组入参、返回字段与排序需要在 API 中显式配置并发布；不能因为平台支持这些机制，就向现有接口随意传 fields、filter、offset 或 IN 数组。先核对接口配置与实际部署版本。需要 Java 调整时，以 QueryServiceHelper 定位主单 ID、BusinessDataServiceHelper 批量加载本页所需字段；数据库索引方案应基于执行计划再定，不预先承诺某个组合索引必然有效。
