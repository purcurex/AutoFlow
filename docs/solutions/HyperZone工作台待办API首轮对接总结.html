01 · 对接结论

首轮已完成可确认字段的代码接入与真实接口验证，五个工作台尚未全量接通。本轮新增销售待支付、待审核收件信息补充，提供15个单据只读查询入口，并核验现有员工授权待办、备货与库存链路。采购、配货、仓库及售后完整清单仍需补齐来源关联、业务状态与独立权限契约。

层级本轮结果
已接入页面待支付、待审核：从履约详情补充收件姓名、电话、订单联系邮箱、城市、邮编、详细地址及国家二字码；保留原订单金额、完整商品、排序与队列口径。
已核验既有链路待支付、待审核、待履约；已履约近一周空页协议；独立员工备货订单及备货库存接口。
已实现只读适配工具14类单据、15个查询操作，含出库列表与详情。严格请求白名单、分页校验、长ID字符串、超时和响应体上限。工具读取成功不等于对应工作台已接通。
保持未开放缺少可靠契约的采购、配货、出库、异常、RMA、采购退货完整清单及审核写操作；不以默认值、空清单或模拟记录替代真实结果。
范围仅工作台待办；未开发数据分析、未修改FOP后台、未执行真实单据审核。现有本地改动保留。

当前常用本地前端仍保持 Mock 模式。真实 FOP 验证通过独立联调进程完成；私有配置已补充履约详情地址，切换 Kingdee 模式后生效。测试凭据保留在本地忽略文件，报告不包含密钥、Token或客户原始记录。

02 · 工作台范围

工作台可用／已验证尚未闭合的功能
销售待支付、待审核分页列表；本轮新增收件信息；独立备货清单。销售已完成、异常、RMA；订单金额拆分；待审核国家及部门筛选的上游全量口径；待支付／待审核完整筛选结果导出。
发运待履约及其阶段筛选既有员工接口；已履约接口响应；有效发运单与物流信息既有契约。已履约有数据样本；原始发运接口新增字段与版本文档同步；包裹取消、RMA补发、缺单与同步失败场景的完整覆盖。
采购独立备货待采购查询链路；采购申请／采购订单原始查询入口。履约待采购、供应商待发货、采购完成、按采购单分组、采购退货；履约与备货旺旺催办的真实采购分录、供应商及联系人数据。
配货配货单按编号查询连通。未齐套、齐套未审核、配货完成；即时库存独立权限；配货审核预检与提交。
仓库出库列表及详情读取真实样本；发货通知查询连通。履约视角待出库、已出库；拦截／取消拦截标签；采购退货及完整来源链。

统一数据口径

  • 主行保持履约订单；SKU搜索命中后展示整单全部商品，采购、RMA、退货单通过稳定来源关系关联。
  • 履约待办按C端付款时间倒序；备货按创建时间倒序；完成清单按相应阶段完成时间筛选与排序。未知时间保持空，不借用其他时间。
  • 同一订单可同时进入业务主流程、异常或售后清单；异常与RMA标记不替代主流程进度。
  • 筛选、数量、汇总、分页与导出使用同一授权范围；共享采购单只累计当前账号可查看的来源行。

03 · 接口实测

测试环境为 hyperzone.test.kdgalaxy.com，核验日期2026-11-09。接口包为2026-11-06历史快照，包内说明明确未重新发布或核验线上。15个只读查询均通过真实请求验证，其中6个读取到记录、9个为精确查询空结果。下表区分有数据样本与空结果验证；空结果仅证明本次请求通过，不能证明返回字段足以支撑清单。

接口实测结果业务接入结论
01 履约详情
queryOrderDetail		HTTP 200、成功；按已授权履约ID返回真实记录。已接收件信息。必填ID，不能作为全量履约列表发现接口。
02 配货单
queryAllocation		HTTP 200、成功；精确非存在编号返回空。文档仅6个抬头字段；有效配货、来源及齐套占用尚未证明。
03 发运单
queryDispatch		HTTP 200、成功；已授权订单关联发运单返回1条。实际含源包裹、订单号、物流及同步字段，多于包内6字段；须补实际Swagger及关联规则。现有待履约仍用员工聚合接口。
04 发货通知
queryDeliveryNotice		HTTP 200、成功；精确查询空结果。需补真实关联样本及WMS下发事实；不能由通知单存在推定已出库。
05 出库详情／列表
queryOutbound
queryOutboundList		两个操作均成功；列表返回2条，按其中单号读取详情返回1条。列表必须传业务起止日期；已修正最初误用详情参数导致的603。仍缺完整授权履约来源链和整单出库完成判定。
06 采购申请
queryPurchaseRequisition		HTTP 200、成功；精确查询空结果。Schema含来源实体／单／行及销售单行ID；需真实样本核对。申请审核不等于采购单已付款。
07 采购订单
queryPurchase		HTTP 200、成功；精确查询空结果。包内仅抬头，无法构造采购单分组、来源数量、付款与供应商发货进度。
08 收货通知
queryReceiptNotice		HTTP 200、成功；精确查询空结果。Schema有销售单行及来源／核心单关联；需核对实物在途、通知和入库的区别。
09 入库单
queryInbound		HTTP 200、成功；精确查询空结果。分录缺来源／核心单ID与行ID；不能仅凭SKU或物料拼接履约需求。
10 收款调整
queryReceiptAdjustment		HTTP 200、成功；精确查询空结果。需与RMA及原履约稳定关联，区分调整申请和已执行退款。
11 收款单
queryReceipt		HTTP 200、成功；精确查询空结果。客户收款与采购退款收款独立；不以付款日期替代C端付款时间。
12 付款单
queryPayment		HTTP 200、成功；精确查询空结果。需采购单来源分摊与付款有效状态；采购付款时间用于催办时效。
13 RMA
queryAfterSaleOrders		HTTP 200、成功；2条真实记录，状态为1、3，类型为C、B。实际状态与包内发货状态枚举冲突；无退款币种。本轮禁用原始状态筛选，不映射成前端售后流程。
14 备货单
queryStockOrder		HTTP 200、成功；2条，仅ID、单号、金额。该原始接口不足以承载待办；页面继续使用字段完整、独立授权的员工备货接口。
15 履约审核
auditFulfillmentOrder		未执行写操作。请求结构已核对；缺员工操作授权、预检版本及幂等结果约定，保持关闭。
16 配货审核
allocation-approval-targets
allocation-approve		未调用预检或写操作。Schema仅空query／command／data对象，当前源码未找到文档指定控制器，不能猜请求结构。

04 · 已落地代码

授权履约详情补充

本地登录账号 → 验证FOP员工绑定 → 员工待办分页与本地范围校验
→ 核验本次组织授权交集 → 按已授权履约ID读取详情
→ 核对单号／客户／业务员／单据类型／状态 → 返回收件信息
展示字段FOP字段处理方式
收件姓名hzkj_customer_first_name＋hzkj_customer_last_name按实际配送字段拼接；空值保持空，不取客户联系人代替。
电话／邮箱hzkj_phone／hzkj_email邮箱为订单联系邮箱；不推定其为独立收件邮箱。
城市／邮编hzkj_city／hzkj_post_code原值展示，不按国家名称或其他资料补造。
详细地址hzkj_address1／hzkj_address2沿用现有收件人弹窗；源系统可能已把第二行拼入第一行。
目的国hzkj_country_twocountrycode只接受明确二字码；缺失为空。尚不启用仅基于当前页国家集合的全量筛选。
省／州待发布 hzkj_state本轮为空；行政区划名称不替代原始省州。

详情读取使用当前员工Token；最多4个并发、30秒总时限、累计16MiB。重复、缺失、非末页、跨客户或状态变化均拒绝本次补充。详情不缓存到其他账号，不作为审核版本证据；当前列表与详情缺少共享快照版本，地址并发修改的一致性仍需上游补齐。

开发联调入口

新增 npm run fop:test-workbench，固定15个只读操作，不接受任意URL或审核动作。出库列表采用独立日期与数组参数；RMA状态参数因契约冲突明确拒绝。单次请求15秒、响应4MiB，禁止重定向与自动重试；日志仅输出成功状态、数量及错误类别。

npm run fop:test-workbench -- --operation order-detail --id '<履约ID>'
npm run fop:test-workbench -- --operation purchase --billno '<采购单号>'
npm run fop:test-workbench -- --operation outbound-list --start-date 2026-11-01 --end-date 2026-11-09
npm run fop:test-workbench -- --operation rma --customer-id '<付款客户ID>'

默认使用 backend/.env.fop.local。仅在需要核对原文时加 --save-response，文件保存至已忽略的 .runtime/fop-workbench/，权限0600。该工具用于研发联调，不是面向普通用户的查询接口，也不替代员工数据授权。

06 · 后台改造

建议在现有员工授权API层补齐待办聚合能力，内部复用业务单据查询；前端继续使用统一工作台模型。无需为每个页面另建业务单据，不在浏览器跨单据拼接权限或计算整单进度。

优先级改造事项交付要求
P0发布实际接口契约重导线上Swagger；校正采购、RMA状态；补全配货审核query／command／data；声明版本、时区、空值和枚举未知值处理。
P0订单发现与资源授权扩大员工待办队列能力，增加采购、配货、仓库、异常与完成记录；明确各资源和操作的独立授权，以及当前客户归属。
P0稳定来源链采购、配货、通知、出入库逐行返回来源实体／ID／行ID／数量／单位；支持一单多品多采购及多履约合并采购，排除失效关联。
P0待办分页与导出先授权、先全量筛选排序后分页；提供同范围汇总、筛选候选、导出ID快照与按ID读取；新增专用待办快照或分页契约，不借分析接口取全量。
P1采购与供应商事实采购分录、供应商、平台单号、付款、发货、退款及催办联系人；整单进度由有效来源行聚合。

P1售后与异常RMA来源、流程和退款币种；采购退货实体及全流程查询；显式异常分类／原因，独立于主流程。

07 · 审核接入

环节明确要求
履约审核目标由授权履约ID定位，服务端生成billno＋org_number；固定履约单类型，调用标准audit。需要FOP独立操作授权，不接受前端任意组织或单号。
配货审核先取唯一有效配货与当前版本，再提交该目标；服务端重验整单齐套、库存占用、来源与有效发运单已审核条件。
并发与幂等相同命令ID与相同内容复用结果；旧版本拒绝。网络超时返回结果待确认，先查单据状态，不自动重放审核。
结果判定HTTP 200不等于审核成功；逐项检查result、billStatus、errors、成功／失败数量，并读回单据状态。
后续单据履约审核后配货可能异步生成；配货审核成功后，发货通知生成失败不回滚审核。必须区分“已审核、下游待处理”，不能再次审核补偿。

履约审核会实际耗用全款备货权益，配货审核涉及库存锁与后续通知生成。本轮未发起真实审核；待上述契约发布后，先使用指定测试单核验权限、版本冲突、超时确认和幂等，再开放页面动作。
