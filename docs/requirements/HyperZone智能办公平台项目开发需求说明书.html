05 · 同步机制与业务边界

5.0 · 时间增量机制（首期）

  1. 初始化衔接：开始前记录源服务器时间 T0，按稳定 ID 遍历实体全集并读取完整单据；随后从 T0 减重叠窗口追赶创建和修改变化，再做全量 ID／内容差异核对。该过程最终收敛，不是冻结快照；初始化中发生删除、跨公司移动及异常回填仍走核对补偿。
  2. 固定窗口：每租户＋公司＋实体保存上次成功截止时间 W。本轮 L=W−重叠窗口，U=源服务器时间−安全延迟；createtime 和 modifytime 两路均查询 [L,U)。建议初值重叠10分钟、安全延迟2分钟，须按实测事务延迟、时钟及接口滞后调整；超过窗口的迟提交／回填由补偿扫描修复。U不大于W时不回退水位，源时钟异常需核查；时间精度未经确认不得截断为秒。两时间均空或非法的记录进入核查，不生成当前时间代替。
  3. 稳定分页：每路固定 U，按该路时间 t、主键 id 升序；下一页条件为 t>lastTime 或（t=lastTime 且 id>lastId），同时保留窗口约束。同秒多单不能只传时间游标；ID按源端类型比较，64位ID不转JavaScript数字。这是稳定游标目标；现有四项API采用普通页码时，须显式启用下述最终一致采集模式，不能宣称无遗漏或稳定快照。
  4. 新增与变更：两路合并按租户＋实体＋稳定主键执行 upsert，保留公司归属；若实体主键只在公司内唯一，再纳入公司主键并显式处理移属。本地无记录即新增，有记录即更新，不按创建日期判断是否已入库。同一时间内容变化仍比较规范化内容，不以时间相等跳过。实体串行执行，禁止较旧源时间覆盖已保存的新事实；并发读冲突回读确认。
  5. 持久化与重跑：分页原文、范围及时间先暂存。两路全部成功、所需详情齐全后，事务保存完整原始单据、旧／新关联投影任务并将采集 W 推进到 U（不是本页最大时间）；展示发布须重算新旧关联订单。四实体普通分页模式已实现同事务发布；必需关系缺失的单据保留待处理，不把采集水位等同全部展示已刷新。失败不推进 W，重启从该窗口重读；缺非必要字段可留空，分页或详情缺失不可当作该窗口完整成功。一次完整空窗口可以推进 U，但响应须明确成功及范围。详情读取到U之后的新内容须记录实际时间，不能标为U时点快照；缺省字段不冒充显式清空。
  6. 独立实体：履约、备货、采购、收货、配货、发运、出入库、资金、RMA及人员归属各自取增量。下游单据变化即重算关联订单，不依赖履约单 modifytime 跟着变；取消关联时同时清理旧关系。分录独立修改若不更新主单时间，则补扫对应实体或小范围修补时间更新。
  7. 删除与补偿：软删除／作废作为状态更新；硬删除优先读取平台删除记录。没有删除记录时定期完整 ID 对账，对差异逐ID确认源端不存在／移出后才使本地失效；失败、无权或不完整扫描禁止批量删除。对账期间新增／修改记录需保护，扫描结束再回查差异；补偿与增量共用写入锁，回填旧时间造成的冲突经源端权威回读确认后修正，不能永远被旧时间拒绝规则挡住。每日完整内容轮检为建议起点，可分批调度，但必须覆盖已完成、关闭、历史单据，不能永远只扫近期修改或未完成订单。

时间展示“最近同步”取已满足源屏障的sourceSyncedAt；多公司取已覆盖的最早时点，未知显示“—”。collected显示“采集时点”。最近查询、后台完成与源数据覆盖时间分别表达。计划任务成功不意味着页面即时更新；当前页面须主动刷新、重新进入，或由本次观察到成功的同步回执触发重查。

8.4 · 去重应按主办事项，不能仅按订单号隐藏

建议后端基于当前本地事实统一计算“当前主办阶段、主办岗位、下一动作、等待原因、并行任务及完成历史”。这是待实施的派生结果，不是FOP已提供字段。普通工作台默认显示当前可办理事项；纯等待项与历史查询单独标识。阶段标签只用于查询，不自动审核、采购、占库或发货。

交叉场景默认展示原则必要例外与防漏单要求
待审＋采购禁止正常待办重叠。履约未审由销售主办。已存在的采购单因源单撤审而失配时保留采购风险核查，不继续正常采购，也不删除既有采购义务。
采购＋未齐套纯缺货等待由采购主办；配货显示等待原因。已有部分库存可进行独立配货时可有可操作子任务；不能用跨岗位全单排他导致剩余商品无人处理。
采购＋入库采购已全发后交仓库，采购完成进入历史。一个供应商已到货、另一个未发货，可同时催发与入库，必须显示不同采购行／通知及剩余量。
齐套＋发运发运未制备时发运主办；配货等待。发运已审后交配货审核。现有FOP确有先发运审核后配货审核门禁，不能反向排列。
同步＋出库两个动作分别判断，不由一个状态替代另一个。若必须并行，各岗位保留不同动作；若确定强制先出库后同步，则改为出库后才生成同步待办，需业务确认并核对FOP执行规则。
多包裹同一任务单位建议公司＋来源实体ID＋包裹／关联单ID＋动作码。包裹A可出库、B仍缺货时，不以整单最早阶段抹掉A。当前列表可继续履约聚合，但需展示有效子任务，整单唯一数与任务数分别统计。
售后＋正向按售后范围和拦截状态处理。部分商品售后与其他商品正向履约可以并行；全单有效拦截则停止受影响执行。关联不明先核查，不靠同SKU推断。
完成＋后续保留完成历史，不纳入待办去重。销售已审＋待采购、采购已发完＋待入库、配货已审＋待出库均合理。

8.5 · 统一判定顺序与来源边界

  1. 先确定公司、身份、岗位和来源业务员权限，读取有效同批次事实；来源缺失或关系不确定进入待核查。
  2. 区分正常正向任务、有效拦截／取消、逆向独立任务；正常正向先过付款及履约审核门禁。
  3. 审核前仅由销售处理付款、准备及审核。审核后根据剩余实物需求、采购进度及可用配货事实判定当前动作；不以“有采购单”取代需求是否准备完成。
  4. 有采购办理事项优先采购；纯等货的配货记录转等待视图。已到货的独立通知可同时由仓库办理。
  5. 齐套后根据发运是否制备且已审，交发运或配货审核；放行后分别产生出库及必要的平台同步事项。
  6. 一个任务只归一个主办岗位；确需并行的子任务说明原因。任何未完成且无主办、无等待原因、无异常归属的记录进入漏单核查。
取数事实优先来源必须关联／待提供的内容
付款与审核履约单hzkj_receipt_status、hzkj_receipt_date、billstatus、hzkj_orderstatus。已付草稿的“采购准备完成”没有独立已确认字段；优先以履约审核作为门禁，不发明新API字段。
采购需求履约头hzkj_purchase_status、明细hzkj_entrypurc_status、hzkj_qty、hzkj_purcqty、hzkj_use_stock。按采购单执行需采购单ID／行、源履约行、下单、支付、供应商发货事实；本单回写不足以得出采购退款或1688付款成功。
齐套与放行明确关联的配货单原生齐套、审核、作废状态。“当前可配货”与“纯等货”需可用库存／配货诊断、缺料原因；现有来源不足时先保留等待／核查，不能凭采购状态猜库存。
发运与同步有效关联发运单审核、包裹、渠道、跟踪号、hzkj_delivery_status及拦截状态。多包裹必须逐包裹匹配；有效跟踪号类型由物流渠道规则决定，不能用任意物流订单号冒充可同步跟踪号。
入库与出库履约整单出库回写；收货通知本单的发货、WMS及行入库量。准确到包裹／明细的可出库量、发货通知放行，以及收货通知入库量需对应单据事实；目前部分字段待提供，不额外在线跨单查询。
逆向任务RMA主单及明确原单关联；正式实物采购退货明细。采购退款候选API仅能说明退款候选，实物退货数量、执行状态、退货物流及采购／仓库责任节点仍待正式接口。

8.7 · 建议实施顺序与需确认事项

第一步应修复用户已明确的审核门禁：同步覆盖待采购、已采购待发货的履约及采购单视角、待建需求、列表total、首页计数和导出，并测试撤审及既有下游单据。第二步统一主办事项与等待原因，优先收窄宽泛待履约及纯缺货配货待办。第三步补齐入库、实物退货、多包裹执行等必要事实。上述其他队列仍为下一轮建议；销售待支付已按后续指令单独落地，见8.9。

待确认建议默认值影响
制备时机默认齐套可推进时转发运制备；确需提前制备的渠道单列并行原因。决定发运何时出现在主待办；无论选择哪种，发运审核都必须先于对应配货审核门禁。
同步与出库先沿用FOP已有两个独立动作，不凭查询层新增强制先后；界面明确标为不同任务。如业务决定只在实物出库后同步，需要同步执行门禁、待办条件和失败补偿一起调整，不能只改前端过滤。
等货可见性默认可执行待办不重复列纯等货；提供“等待采购／到货”跟踪入口。保留配货积压和账龄追踪，同时避免给两个岗位派发同一个无法推进的任务。
退货职责采购负责业务协商／退款跟进，仓库负责审批放行后的实物退货出库。必须由正式退货接口提供阶段与数量后确认，不以退款状态推断实物动作。
