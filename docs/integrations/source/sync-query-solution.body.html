当前接口包未见覆盖全部业务单据的通用变更游标或更新时间增量查询；现有接口授权成功不等于具备可靠增量同步能力。FOP 需补齐变更采集、初始化衔接和完整事实读取，前端业务范围筛选由本项目执行。

02 · 方案对比

对比前提统一为：集成账号调用 FOP，本地组织和角色为账号权限依据。实时穿透查询指本项目后端计算允许的业务员范围，将条件交给 FOP，由 FOP 完成关联、筛选、排序、统计及分页，再返回结果；并不必然要求复制一套 FOP 组织。

FOP 系统负载优以业务变化量、初始化和核对量为主；初始化、补偿仍需控制负载。劣以查询次数和复杂度为主；工作台刷新、导出可能重复执行关联与合计。

复杂待办分类优在本项目集中组合采购、发运、配货等事实，复用现有业务规则。劣通常需 FOP 实现相应查询口径；也可本项目补算，但必须保证分页与合计正确。
组织权限平本项目将本地成员范围直接用于数据库查询，员工调动和角色变更可在下次请求生效。平本项目计算成员范围，FOP 按受信任条件在分页前过滤；两端共同校验范围。
FOP 归属与撤权劣归属变化受同步延迟影响；集成资源授权需独立复验或即时撤权通知，不能依赖旧副本永久放行。优可在请求时校验最新 FOP 归属和资源授权；是否即时取决于接口实际实现。
数据一致性劣最终一致；需版本、防乱序、跨单据依赖及完整结果发布机制。优单次数据库查询可读取一致视图；多接口拼接也可能出现中间状态，需快照或版本约定。
搜索、筛选扩展优已有事实足够时主要修改本项目；缺失源字段仍需 FOP 补充。劣新筛选涉及 FOP 查询参数、谓词、统计和分页契约时，两端联动修改。
列表与导出一致平复用本地授权查询与数据版本；导出开始及交付前复验账号权限。平FOP 需为列表、汇总、全量导出提供一致条件和范围，避免只导出当前页。
FOP 短时故障优在约定的授权与数据时效内可查询上一完整结果，并显示同步状态；超限停止相关查询。劣未命中有效缓存的查询通常不可用；故障影响直接传到页面。
历史重算优可从已同步事实重建查询结果，便于修正规则；原始事实缺失时需要回源。劣修改规则后需重新读取或由 FOP 重算；本项目不承担持久副本维护。
数据存储与保护劣增加一份公司业务副本，需访问控制、备份、删除传播与保留期限管理。优本项目可少存业务数据，副本治理负担较小；日志和缓存仍需受控。
运维复杂度劣需管理同步进度、积压、失败重试、校准、存储和重建。优主要管理接口性能、授权、限流和可用性；无完整同步管道。
初次交付平需要查询库和可靠同步基础；不能仅删除现有权限校验就上线。平若 FOP 已具备完整工作台接口，首次交付可能更快；目前字段与范围契约尚未全部具备。
本项目适配度优多工作台、多角色、高频查询、复杂关联及持续演进的展示规则。劣对读取时状态要求严格、查询量适中、FOP 已有成熟查询能力的页面和操作校验。

每次请求先从 FOP 拉取全部历史、再在本项目内存中过滤，既不是高效的穿透查询，也不是本方案。此前管理员读取约 31,900 行、约 91 秒触发完整性上限，是这一读取路径的历史联调证据，不能直接用于推算增量方案或优化后 FOP 查询的性能。

05 · 同步与初始化

5.1 初始化衔接（本项目已实现，源服务待提供）

  1. FOP 开始可靠保留变更，取得可续传起点 C0，并确认保留期限覆盖初始化全过程。
  2. 导出与水位可衔接的公司数据快照，导入本项目暂存区域，校验单据、分录及关联完整性。
  3. 从对应水位回放初始化期间的变化，按单据版本避免旧快照或旧事件覆盖新数据。
  4. 追平增量，核对来源数量、关键状态及抽样金额，建立工作台查询数据。
  5. 验证通过后发布完整查询版本，切换页面读取；后续持续增量更新。

已有备份只有在备份时点有匹配水位、后续变更完整保留时才能直接恢复后续传。没有匹配水位，需要重新生成可衔接快照或执行全量重建。FOP 数据库备份不能直接假定与本项目 PostgreSQL 查询表兼容，应通过受控导出和映射导入。

5.2 增量处理

现有发布器接收已归一化提交组，在一个事务内完成单据、分录、关联、清单投影及游标更新；不是 FOP 接口解析器。待入库同单投影的发布、主数据及独立授权写入器仍须补齐。以下为源端接入后的处理要求。

  1. 产生：所有受支持的新增、修改、审核／反审核、作废、删除及归属变化产生持久变更；覆盖人工、API 和后台任务。
  2. 拉取：同步进程按公司和实体流读取游标之后的已提交变更；有积压连续追赶，空闲时等待下一轮。
  3. 落地：整页变更可靠写入本地收件表后，提交“已接收游标”；按事件 ID 去重。
  4. 应用：按来源版本更新主表、分录和关系，合并受影响履约订单的重算任务；同一订单的任务串行或受版本约束执行。
  5. 发布：关联事实具备后，事务更新订单查询数据及待办分类；推进连续已处理的“已应用水位”，通知页面重新查询。

已接收不代表页面已更新。监控和页面时效以已应用水位为准；失败事件保留重试任务，不能跳过后把后续游标表述为全部应用完成。跨单据暂未齐备时保留明确的待补状态，不把 unknown 推定为未采购、未付款或已完成。

同一源事务涉及多张单据时，应提供变更组标识及组完成边界，或可验证的依赖版本／一致快照；本地收到所需版本后再发布该组结果。跨源事务的业务链采用最终一致，不承诺瞬时一致。FOP 暂不能提供完整边界时，明确允许短暂中间态，缺少可确认依赖时不发布新的完成判断，不能仅凭关联记录已存在认定全部变化已追平。

5.3 采集方式

优先使用 FOP 可可靠落地的事务变更记录或受支持的 CDC，提交后对外提供稳定游标。若使用事务发件箱，应由 FOP 开发核实苍穹事务扩展点，保证业务保存与变更登记原子性；不能仅在页面按钮或 HTTP 控制器回调中发送通知。参考：事务发件箱模式。

对外游标必须保证不漏掉晚提交事务，不能直接将最大单据 ID、最大预分配事件 ID 或客户付款时间当成同步水位。仅具备更新时间接口时，可用“固定扫描上界＋更新时间与 ID 排序＋重叠窗口＋版本去重＋周期核对”过渡，但必须验证分录更新是否更新主表时间、物理删除是否可发现；该方式不等价于可靠提交日志。

同步按已确认的导航触发、手工触发及低频兜底计划执行；前台列表先读本地。源端追赶耗时、列表延迟和历史导入吞吐须在恢复测试后测量，不将本地 Mock 耗时作为 FOP 性能指标。

场景处理策略边界
收款、审核、采购、配货、出库变化同一增量流持续接收；按业务紧急性调度处理，监控最老未应用事件。高优先级事件可先处理，但不能把连续已应用水位跨过未完成事件。
拦截、取消及仓库执行优先同步展示；若提供通知，唤醒拉取；实际执行回 FOP 校验最新状态。不以同步页面代替 FOP 出库拦截。要求更短展示延迟时需专项压测和事件通知。
商品名称、图片及其他基础资料按变化同步，低优先级处理；相同资料合并更新。不允许业务员归属、资源撤权作为普通低优先级资料长期排队。
页面刷新SSE 发送授权范围内的版本提醒，页面重新查询；定时刷新作为补偿。不推送公司全量业务载荷；断线后重新查询，避免遗漏提醒导致页面不更新。
历史核对与重建低峰、分批、限速运行，与实时增量使用独立任务优先级。不能让初始化、导出或修复挤占实时处理能力。

每天 10 万条变更平均约 1.16 条／秒，但这不是 10 万张订单：一张订单可引起多种单据和多次状态变化。容量评估以实测峰值事件量、平均载荷、关系扇出、重算耗时与保留天数为依据，不能仅按日均数选型。

同步消费能力应持续高于峰值产生速率并留有追赶余量。中断期间积压为 B、恢复消费速率为 μ、同期新增速率为 λ 时，理想追赶耗时约为 B ÷ (μ − λ)，仅在 μ > λ 时成立，还需计入限流及失败重试。批量大小、并发和限速以 FOP 实测配额为准，不预设其支持无限并发。

07 · 本地查询

7.1 查询数据结构

逻辑数据保存内容职责
来源单据与分录公司、实体、源 ID、版本、业务字段、删除标记保留可追溯事实；主分录一并替换或按明确版本更新，避免遗留已删商品。
来源关系履约／备货单、来源行、采购行及关联数量维护一对多、多对多，支持反向定位受影响订单。
工作台查询数据订单主行、商品检索、业务员、付款时间、仓库、阶段与关联摘要支撑五工作台、卡片、筛选、合计、分页及导出。
同步与修复任务接收／应用进度、事件去重、重算任务、失败原因和重试状态恢复、校准、监控；生产备份需与已接收事件一起保持一致。

基于既有 NestJS、TypeORM 和 PostgreSQL 实现，先用独立同步进程与持久任务表；达到实测瓶颈后再引入消息平台。按公司、业务员、待办阶段、客户付款时间和来源关系建立必要索引；SKU 命中采用订单级查询，展示整单全部商品。

7.2 业务口径

  • 履约订单为主要展示视角；一张采购单影响多笔履约订单时，按来源行分摊并重算相关订单，不复制整张采购单数量或金额。
  • 待办与完成分类复用本项目已确认的业务事实规则，异常／RMA 标记不擅自改变主流程。销售已审核清单按履约单单据状态已审核，不以已支付、已发货等业务状态排除。
  • 近一周／近一月／近三月统一按关联成功客户收款的实际支付时间。当前已核对来源为 hzkj_receive_bill.hzkj_receive_time，来源分录 A 对履约、C 对备货；公司、来源类型、来源单号精确关联，排除作废及不符合业务口径的收款，多笔符合条件的取最近一笔。
  • 缺实际付款时间不使用创建、审核、采购付款或旧源单时间补齐。UTC+8 统一归属；履约默认客户付款倒序，独立备货保留已确认的创建时间默认排序。
  • 金额、退款币种、物流渠道、Shopify 同步结果和采购完成事实缺失时，保留未知或未接通，不以同步架构补造业务事实。

采购阶段完成：供应商全部已发货。履约单视角按本单采购需求全部发出判断；采购单视角按整张采购单全部有效 SKU 已发出、未发数量为 0 判断。部分发货不算完成，不等待收货或入库。本地采购单组头已按全部有效采购分录汇总，展开履约明细独立分页；销售订单编号去重统计履约笔数。缺少整单来源、数量或完整授权时明确不可用，未知发货事实不推定完成。

配货完成清单：“审核状态”直接采用有效关联配货单的审核状态，审核时间采用配货单 auditdate，两项来源已确认；不使用固定“已完成”标签或阶段完成时间替代。多张配货单须全部已审核，展示最近审核时间；任一时间缺失保留空值，撤销审核后移出本清单。

待入库按收货通知单展示：收货仓库取表头 hzkj_ware_house，供应商取采购信息页 hzkj_providersupplier，物流信息取本单 hzkj_logistics_company＋hzkj_waybill_number，表示供应商发往国内仓库的快递包裹。同步落入通知单及同单投影，页面查询本地数据；不复用履约发货仓、渠道或跟踪号。上述来源已核对，真实同步写入待接通。

待出库与已出库清单保持履约订单视角，一单一行。物流信息读取有效关联、未删除且已审核（billstatus=C）的发运单：实际渠道、全程及尾程跟踪号按发运单逐组展示；撤审、删除或解除关联立即移除对应物流，不回退履约包裹渠道或旧号码。分页、计数、SKU 整单搜索和导出仍以履约订单为单位。

履约订单原生状态：履约订单视角的采购状态直接读取本地 hz_fop_fulfillment_orders.raw_purchase_status（FOP 表头 hzkj_purchase_status）：0 未采购、1 部分采购、2 已采购、3 已入库、4 已发货。已采购不等于采购款已付或1688下单成功，具体采购进度仍使用独立付款／下单事实。待采购与已采购待发货限0／1／2；采购完成取4并保留后续3，排除无需新采购的备货库存订单。仓库出库状态读取 raw_delivery_status（表头 hzkj_delivery_status）：0 未出库、1 部分出库、2 已出库，不能使用分录 hzkj_outbound_status 替代；历史部分出库如实展示，不新增部分出库操作。待出库筛选含0／1并排除拦截发货，完成取2；缺失原生状态提示数据未就绪，不默认未采购／未出库。列表、导出与本地查询口径一致；采购单、收货通知单视角保持各自主单来源。真实同步写入仍未接通。

7.3 物流渠道与取号

阶段／动作业务事实本地展示与更新
待支付履约单物流决策中的自定义物流渠道展示自定义物流渠道名称。
待审核客户运费报价可设置默认实际渠道，订单同步时写入包裹实际渠道；审核时确认后续发货渠道，尚未取号。Customer 后依次为物流信息、发货仓库；直接分行展示英文自定义渠道、中文实际渠道，无类型前缀，不显示跟踪号。Excel 同口径；缺实际渠道保留空值。
已审核清单履约订单已完成审核操作，后续采购、发运、出库不影响其归属。沿用待审核列顺序与渠道展示；有有效跟踪号则显示，无号显示“尚未获取”。
制作发运单获取物流跟踪号并回写订单；实际发运渠道可与审核时渠道不同。同步发运单渠道、号码及对应关系；发运清单取发运单渠道，全程号标 QC、尾程号标 WC。
删除发运单清空对应物流跟踪号。同批变更撤销旧发运关联和号码，清空包裹号码镜像，重算受影响订单；空值覆盖旧值。
重建发运单重新取号并更新对应订单。按新发运单及包裹关联写入新号码，不复用旧号码，不按数组位置猜配。

查询仅读取本地已发布数据；跟踪号须关联有效且未删除的发运单，不从旧包裹镜像回退。验收覆盖“默认渠道已有、待审核无号码”“删除后无旧号码”“重建后仅新号码”；真实同步适配尚未接通，目前以隔离 Mock 和本地回归验证。

7.4 列表、库存与导出

执行顺序统一为当前授权范围 → 业务分类与查询条件 → 合计与排序 → 分页。库存同时校验客户、SKU、仓库及独立库存资源；选中订单只查选中客户和 SKU，未选订单按现有业务规则查询。催办联系人和发起动作仍校验当前订单、采购关系与权限。

导出默认使用全部符合筛选且获授权的数据，选中导出重新核验全部选中订单。导出使用同一数据版本或一致快照，结果记录数据截至时间；交付前复验当前账号、组织和资源授权。权限收窄、来源关系变化导致选择失效时重新查询，不静默导出无权或部分数据。

来源事实用于形成只读查询数据，实际办理保留 FOP 链接或单号入口。对单条记录回源刷新时先本地授权，再按确定的公司和 ID 读取；不允许因本地缺数或权限失败，自动改成不受范围限制的全量透传。参考：可重建查询视图。

08 · 接口约定

下表为建议新增或扩展的能力，不是已经发布的 API 路径。现有人员目录和资源授权接口优先复用；新增接口只对受信任的后端集成应用开放。

接口能力必要内容交付方
初始化快照公司、实体范围、快照标识、可衔接水位、稳定分批读取、完成核验信息。FOP 导出或接口；本项目导入与发布。
统一变更查询输入 afterCursor、公司／实体范围和 limit；输出事件、nextCursor、hasMore、服务端时间、保留边界、源端提交／采集覆盖进度、已发布流头及采集健康。空批次同样返回健康与进度；游标与范围绑定，过期明确返回重建要求。FOP。
批量单据快照按实体与 ID 集合读取主表、完整分录、版本、来源关系；逐项区分存在、删除、无权及失败。变更事件已携带完整版本快照时可减少回查。FOP 扩展现有查询；本项目按版本应用。
核对与补读按公司、实体和稳定分段返回 ID／版本或摘要，支持定位缺失与删除；不能只比较总条数。FOP 提供可核对入口；本项目修复。
人员及资源授权工号、记录 ID、masterId、启用状态、当前公司与资源授权；权限变更可识别。复用并核验现有 FOP 接口。
变更字段约定
eventId／streamCursor事件唯一，游标不透明且可续传；由 FOP 保证遍历已提交变更不遗漏。跨实体流各自记录进度。
companyId／entityType／entityId稳定来源标识，不能把单号、工号、人员 ID 与单据 ID 混用。
operation／sourceVersionoperation 固定为 upsert 或 delete；作废是带明确业务状态的 upsert。版本单调可比较，或提供等价的可靠先后关系。
committedAt／schemaVersion明确时区的提交时间与数据结构版本；采集落后也应计入时效，不能只测 API 返回速度。
changeGroup／依赖版本同一事务的变更组标识与完整边界，或可验证的依赖版本／一致快照；不以单据存在替代跨单据完整性确认。跨事务链路保留最终一致边界。
payload／关联线索完整版本快照或批量回查依据；删除和解除关联需保留可定位旧关系的线索，使原关联订单重新计算。

建议变更日志保留至少 7 天，最终期限按可接受的最长停机、初始化耗时和源端容量确认；若初始化或停机可能超过 7 天，必须延长。超过保留边界进入重新校准／初始化流程，不从当前时刻静默续跑。推送通知仅用于唤醒拉取，可靠恢复仍以持久日志和游标为准。

空列表、hasMore=false 或最新服务端时间，只能说明当前已发布流的读取结果，不能证明上游采集器没有故障。时效与过期判定须联合源端采集覆盖进度、采集健康和本地应用进度；正常无业务变化时，有效健康证明可确认数据仍新鲜，不按最后一笔业务发生时间误判过期。

09 · 故障与恢复

情况处理结果
Token 失效、接口超时、限流统一刷新令牌或退避重试；不丢任务、不推进失败页面的接收进度，限制并发避免重试放大。
重复、乱序或批量部分失败事件去重、版本检查、逐项持久重试；不把部分成功标为整页或整条业务链成功。
进程崩溃或数据库恢复用同一备份中的游标、收件表和来源数据恢复；重复回放安全。查询数据可重建，备份水位过期则重新初始化。
删除、作废、来源解除更新来源事实与关系，并重算所有原关联订单；不能只新增记录、不移出已失效待办。
依赖缺失或字段无法映射建立待补任务和明确原因；未完整接通的清单不返回伪造的 0 或错误完成状态。
授权变更或账号停用本地权限立即重算；公司／资源授权不再有效时停止相关查询。无法确定新归属的记录不分配给普通业务账号。
持续积压或 FOP 故障显示最近完整数据与延迟；来源恢复后追赶。按最近满足的源水位显示已确认截至时间，未取得来源证明时不伪造新鲜度；资源授权执行独立短有效期。
核对发现差异按公司、实体和分段定位缺失 ID／版本，补读后重算；差异修复不触发用户页面全量回源。

正常运行时周期核对近期变化及未完成业务链，低峰分段核对历史；核对频率和范围按源端能力设置。不能只核对“近期付款订单”，否则会遗漏旧单的新采购、出库或售后变化。变更表、来源表与工作台结果均保留可追溯版本，不在普通日志中记录 Token、密钥或整份收件人信息。

10 · 部署与运维

首期部署为现有 Web／API 服务、独立同步 Worker、PostgreSQL 三部分。查询与同步使用有界连接池和独立任务优先级；多个 Worker 使用租约与任务领取锁，避免重复扫描和同时推进同一游标。事件可重复投递，但实际应用必须幂等。

运维项关注内容
同步健康源端最新已提交／已发布水位、本地已接收与已应用水位、端到端延迟、最老未处理事件、积压数量。
处理能力事件接收／应用速率、来源关联扇出、重算耗时、失败与重试量、源端限流、数据库写入与查询耗时。
数据完整性核对差异、待补依赖、来源缺字段、日志剩余保留时间及快照版本。
权限与会话账号停用、组织／角色版本、资源授权有效期、当前消费者范围；切换身份清除旧缓存并废弃旧请求。

生产由统一后端同步一次，所有员工共用查询服务。协同开发优先连接共享测试后端；需要独立本地同步时使用独立消费者 ID、明确测试范围和限速，避免每台开发电脑反复扫描同一份全量数据。

Git 仅同步代码、迁移与配置示例。业务副本、数据库备份、密钥和 Token 不入仓库；生产业务副本使用受控数据库权限和备份。查询数据可按批准期限归档，FOP 的删除与脱敏要求同步传递到本地副本及对应备份管理。

11 · 实施与验收

阶段主要工作通过条件
1．契约确认确认变更采集扩展点、稳定游标、单据版本、来源关系、资源授权和日志保留；梳理现有字段缺口。FOP 与本项目可演示新增、修改、反审核、删除及归属变更，包含晚提交与失败恢复。
2．最小业务链以履约订单＋客户收款＋销售待办／完成记录跑通初始化、增量、权限和导出。按当前客户付款时间口径，与 FOP 来源事实逐单核对；无跨人、跨部门及跨公司泄露。
3．五台扩展接入采购、收货、库存、配货、发运、出库、备货、RMA 和采购退货的已确认事实。覆盖一单多品、多采购单、采购合并、异常并存、取消拦截及来源变更。
4．并行核对原查询和同步查询后台对照；差异逐项归因，不将两份不同时刻结果直接判错。相同范围、口径与数据时点下，订单集合、金额、分类、总数、分页和导出一致。
5．压测切换按实测日增、高峰、并发和积压场景压测；管理员验证全部工作台，其他角色用后端权限用例覆盖。达到约定时效、查询和追赶目标；故障演练通过，按工作台或公司受控切换。

切换采用显式数据源开关和可回滚迁移。只有原接口能保证同一权限、完整范围及业务口径时才允许回退；不能回退到逐请求全量扫描或不同时间口径。历史文档中的“普通员工必须本人 Token”和“必须 FOP 员工集合筛选”要求，在同步模式上线后由新验证链路替代，原有路径继续保留对应校验直到停用。

验收维度必要场景
