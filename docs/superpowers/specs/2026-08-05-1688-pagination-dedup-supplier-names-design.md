# 1688 分页稳定、商品去重与供应商名称设计

日期：2026-08-05  
状态：用户已确认实施

## 1. 问题与证据

当前每个分页请求都会使用 1688 本次响应中的 `totalRecords` 和 `totalPage` 覆盖搜索记录，导致翻页过程中总条数和总页数变化。用户允许商品实时变化带来的少量误差，因此本次搜索应使用第一页结果作为稳定分页快照。

当前商品详情只请求每页前 5 个商品。实际 1688 搜索列表响应包含 `sellerDataInfo` 等评分信息，但不包含供应商公司名称；商品详情响应才包含 `companyName`。因此要让每页所有商品展示供应商名称，必须查询当前页全部有效商品的详情。

现有去重只依赖同一搜索内的 1688 `offerId`。业务要求还要识别同一供应商发布的核心商品信息完全相同的重复商品，同时不能因为供应商相同而删除其不同商品，也不能把不同供应商的相似商品合并。

翻页时整体搜索通常已经完成，但当前分页处于 `pending` 或 `running`。页面只判断整体搜索状态，可能先显示空结果，再在轮询后显示商品。

## 2. 目标与边界

本次修改只完成以下内容：

1. 每次新搜索以第一页的总条数和总页数作为稳定快照，后续页只记录差异日志。
2. 点击重新寻源或修改每页条数时继续创建独立的新搜索，重新取得第一页快照；历史搜索不修改。
3. 同一搜索内优先按 `offerId` 去重；供应商身份明确且核心商品字段完全一致时，使用商品指纹补充去重。
4. 当前页所有有效商品都查询详情并持久化供应商公司名称。
5. 商品详情查询使用固定并发上限，单个详情失败不使整页失败。
6. 翻页期间显示寻源加载态，只有分页成功且结果确实为空时才显示空结果。

不新增供应商店铺地址、评分等页面需求，不修改客户发现、客户联系方式、`contactScore` 或客户综合评分，不升级无关依赖。

## 3. 后端设计

### 3.1 稳定分页快照

第一页成功时写入 `totalRecords` 和 `totalPages`。后续分页只有在原值为空时才补写，否则保留第一页值。若提供方后续返回不同总数，日志同时记录搜索 ID、页码、原总数和新总数，便于定位提供方波动。

重新寻源沿用现有 `force: true` 行为创建新的 `sourcing_searches` 记录，新搜索的第一页重新建立快照。去重范围和分页快照范围都限定在新搜索 ID 内。

### 3.2 商品去重

继续保留 `(search_id, provider, offer_id)` 唯一约束作为强去重规则。

新增可空的 `product_fingerprint`：只有供应商存在稳定身份（优先 `openId`，其次标准化公司名称），并且标题、主图、分类、价格区间、起订量等核心字段具备可比较值时才生成。指纹由标准化字段计算 SHA-256，同一搜索和提供方内增加部分唯一索引。

- 同一供应商、不同核心商品字段：保留。
- 不同供应商、商品字段相同：保留。
- 同一供应商、核心字段完全相同：保留首次出现的记录。
- 供应商身份或核心字段不足：不使用推断指纹，只按 `offerId` 去重。

后续页因去重可能少于页面条数，这是稳定快照允许的少量误差，不回写总条数。

### 3.3 全量供应商名称

搜索页返回后，对当前页全部有效 `offerId` 调用商品详情接口。详情请求使用最多 5 个并发槽位，避免 50 个请求同时冲击 1688。结果使用 `Promise.allSettled` 语义隔离单商品失败：

- 成功：使用详情中的 `seller.companyName` 创建或复用供应商记录，并在前端展示。
- 失败：该商品仍持久化，`detailStatus=failed`，供应商名称为空；不让整页失败。
- 缺少 `offerId`：沿用现有规则跳过该商品。

页面需要供应商名称，但现有商品详情还用于商品标题、价格、MOQ 和评分补充。为保持同页结果一致，所有成功详情继续走现有统一映射，不再保留“前 5 个完整、其余仅搜索字段”的差异。

## 4. 前端设计

未缓存分页点击后立即进入 `pageChanging`。展示条件使用 `pageChanging || pagination.status in pending/running`，商品区域显示现有旋转寻源状态；分页按钮和每页条数选择在当前页加载期间禁用。

已缓存页面直接展示。分页成功且结果为零时才显示空结果。供应商名称继续使用 `companyName -> shopName` 的既有回退顺序；详情失败时不伪造供应商名称，显示现有“暂无”文案。

## 5. 错误处理与性能

- 当前页最多产生与页面商品数相同的详情请求：10、20 或 50 次。
- 并发固定为 5，避免无界并发和明显限流风险。
- Worker 现有心跳持续续租，长分页执行仍由租约保护。
- 单商品详情失败不触发整页重试；重新加载当前页或重新寻源会再次尝试。
- 日志不输出 AppSecret、AccessToken、签名或原始详情响应。

## 6. 测试与验收

自动化测试覆盖：

1. 第 2 页提供方总数变化时，搜索仍保留第一页快照。
2. 每页超过 5 个商品时，每个有效商品都调用详情接口，且同时执行数不超过 5。
3. 单个详情失败时其他商品及分页仍成功。
4. 同一 `offerId` 去重；同一供应商且核心字段完全相同去重；不同供应商不误删。
5. 未缓存页请求后立即显示寻源状态，不显示空结果；加载完成后恢复分页操作。
6. 后端相关测试、前端相关测试、lint 和构建全部通过。
