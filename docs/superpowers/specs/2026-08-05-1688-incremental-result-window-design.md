# 1688 分批结果窗口设计

## 目标

保持现有 1688 服务端分页和缓存机制，只将单次搜索可访问的结果范围分批开放：初始 100 条，用户主动继续寻找时每次增加 100 条。这样不会让第一页等待全量拉取，并能在用户不继续浏览时减少 1688 搜索与详情接口流量。

## 数据模型与分页语义

- `sourcing_searches` 新增 `result_limit`，默认 100，表示当前搜索允许访问的最大结果序号。
- 现有 `total_records`、`total_pages` 继续保存 1688 第一页返回的原始预计总量，不改变历史语义。
- API 响应中的 `pagination.totalRecords` 和 `pagination.totalPages` 表示当前已开放范围：`min(providerTotalRecords, resultLimit)` 及其页数。
- API 额外返回 `providerTotalRecords`、`resultLimit`、`canExpand`，让页面显示“当前开放 100 条 / 1688 预计匹配 536 条”。
- 当 1688 未返回总量时，分页仍等待第一页完成，且暂不允许扩展。

## 扩展流程

- 新增当前用户、当前工作流、当前搜索范围内的扩展接口。
- 前端传递 `targetLimit = currentResultLimit + 100`，后端只允许增加一个 100 条窗口，并使用事务与行锁更新。
- 重复提交同一个 `targetLimit` 返回当前状态，不会重复增加，防止双击或网络重试造成一次扩展 200 条。
- 扩展只开放页码，不立即请求 1688；前端随后进入下一页，沿用“当前搜索已加载页 -> 6 小时历史页缓存 -> 真实 1688 请求”的既有顺序。
- 达到 1688 预计总量后不再显示扩展按钮。

## 前端交互

- 保留现有每页 10/20/50 条选择，默认 20 条；因此默认每批 100 条对应 5 页。
- 分页区显示当前范围、当前开放量和 1688 预计匹配量。
- 仅在当前开放范围最后一页且 `canExpand=true` 时显示“继续寻找 100 条”。
- 点击后按钮进入“正在继续寻找…”状态，扩展成功后自动进入下一页并显示现有“寻源中”加载效果。
- 重新寻源创建新的搜索，结果窗口重置为 100 条，第 1 页保持实时查询。

## 异常与兼容

- 超出开放页码的请求返回 400；越权搜索仍按现有用户和工作流隔离返回 404。
- 扩展目标非法、跨越多个窗口或早于第一页总量返回时返回 400。
- 历史搜索通过迁移默认获得 100 条窗口；不会删除已保存的历史商品或供应商数据。
- 不修改 1688 Param2 适配器、图片字节上传到 `imageId` 的边界、供应商详情策略和缓存有效期。

## 验证

- 后端覆盖初始 100 条、不同 pageSize 的开放页数、低于 100 条、扩展幂等、非法跨级、并发更新和页码拦截。
- 前端覆盖开放量提示、末页扩展按钮、加载态、自动进入下一页、无更多结果时隐藏按钮。
- 最终执行全量测试、lint、构建、迁移检查与本地健康检查。
