# 工作流修订页数据回显修复设计

## 背景

工作流修订页面通过路由参数 `reviseId` 加载原工作流，并把名称、种子类型、关键词或图片 URL、目标市场及 Google 搜索选项回填到表单。

当前页面挂载时先等待工作流列表请求 `fetchWorkflows()`，之后才调用详情请求 `getWorkflow(reviseId)`。列表请求位于详情加载的异常处理之外；当开发服务重启、网络短暂不可用或列表接口失败时，挂载流程会直接中断，详情接口不会调用，页面保持默认空表单且没有加载失败提示。

现场验证表明，详情接口能够返回目标工作流，刷新成功时名称和关键词可正常回显。因此本次只修复前端加载依赖，不修改后端接口、数据库结构、1688 寻源逻辑或工作流业务规则。

## 目标

- 修订页不依赖工作流列表接口即可加载原工作流详情。
- 详情加载成功后回显原有全部表单字段。
- 详情加载失败时显示现有的“加载工作流失败”提示。
- 列表页仍按原方式加载工作流列表。
- 保持创建页、提交修订、启动发现和1688寻源流程不变。

## 方案

采用已确认的方案 1：按页面用途分流加载。

1. 当存在 `reviseId` 时，页面直接调用 `store.getWorkflow(reviseId)`。
2. 详情成功后继续沿用现有赋值逻辑，设置 `revisionSource`、表单字段和种子类型缓存。
3. 详情请求及字段回填保留在独立的 `try/catch` 中，失败时写入现有 `workflows.loadFailed` 提示。
4. 仅工作流列表页调用 `store.fetchWorkflows()`；修订页不再用列表请求作为详情请求的前置条件。
5. 不增加自动重试、后端聚合接口或新的全局状态，避免扩大改动范围。

## 数据流

### 修订页

`reviseId` → `GET /api/autoflow/workflows/:id` → 校验工作流是否允许修订 → 回填表单。

### 列表页

无 `create` 且无 `reviseId` → `GET /api/autoflow/workflows` → 更新工作流列表。

### 创建页

`create=true` 且无 `reviseId` → 使用表单默认值，不为回显目的请求工作流列表。

## 异常处理

- 详情接口不存在、无权访问或网络失败：显示现有加载失败提示，保持表单不可提交状态。
- 工作流状态不允许修订：显示现有“原工作流不存在或不可访问”提示。
- 列表接口失败：只影响列表页，不再影响修订页详情加载。

## 测试设计

新增前端回归测试，至少覆盖：

1. 修订页挂载后直接请求指定工作流详情。
2. 详情返回后，名称、种子类型、种子值、目标市场和 Google 搜索选项正确回显。
3. 修订页不调用工作流列表接口，证明列表失败不会阻断详情回显。
4. 详情请求失败时显示现有加载失败提示。

完成后运行相关前端单元测试、完整前端测试、类型检查或构建，并在本地页面重新加载验证实际回显。

## 影响范围

仅修改工作流页面的初始化加载逻辑及对应前端测试。后端接口契约、数据库、工作流创建与修订请求体、1688配置和寻源流程均不受影响。
