# 本机图片客户发现双模式设计

## 背景与目标

图片工作流包含两条相互独立的业务链路：

1. 1688 图片寻源读取受控的本机上传文件，将图片字节上传到 1688，再使用返回的 `imageId` 搜索商品。
2. 客户发现把图片 URL 交给 PipiAds、Google Lens；第三方服务必须能从公网访问该 URL。

当前编排先执行客户发现，再启动 1688 寻源。当上传图片只有本机地址且未配置公开的 `PUBLIC_ASSET_BASE_URL` 时，客户发现直接抛错，后续1688寻源无法启动，整个工作流被错误标记为失败。

本次目标是实现“双模式”：

- 公网图片模式：正常调用 PipiAds、Google Lens，并执行1688寻源。
- 本机图片模式：跳过 PipiAds、Google Lens，继续执行1688寻源，工作流不失败。
- 页面明确区分1688寻源状态与客户发现状态。
- 不使用1688商品标题生成客户搜索关键词。

## 方案比较

### 方案一：编排层显式跳过客户发现（采用）

客户发现服务返回“已执行”或“因缺少公网图片而跳过”的判别结果；工作流编排根据结果更新步骤状态，并独立启动1688寻源。

优点是状态可追踪、可测试，不把预期业务分支伪装成异常，也不需要数据库迁移。缺点是需要同步调整后端响应类型和前端状态展示。

### 方案二：客户发现服务内部吞掉异常并返回空结果

改动较少，但工作流步骤会被记录成“成功且0结果”，无法区分“确实没有客户”和“根本未执行客户发现”，不符合业务可观察性要求。

### 方案三：为工作流新增运行模式与客户发现状态字段

状态最显式，但需要实体字段、数据库迁移及历史数据回填。现有 `workflow_steps.status/output` 已能表达该状态，因此本次不采用。

## 后端设计

### 1. 客户发现执行结果

在发现模块引入判别结果：

```ts
type CustomerDiscoveryResult =
  | { status: 'completed'; evidence: DiscoveryEvidenceResult }
  | {
      status: 'skipped'
      reasonCode: 'public_image_not_configured'
      reason: string
      evidence: DiscoveryEvidenceResult
    }
```

判断规则：

- 关键词工作流：继续执行客户发现。
- 没有本机资产字段的公开图片 URL：继续执行客户发现。
- 有本机资产字段，且 `PUBLIC_ASSET_BASE_URL` 是可公开访问的 HTTP/HTTPS 地址：使用 `PUBLIC_ASSET_BASE_URL + seedAssetPath` 执行客户发现。
- 有本机资产字段，但公网基址缺失、无效、指向 localhost 或私网：返回 `skipped`，不得调用 PipiAds、Google Lens。
- `seedAssetPath` 不属于当前用户或路径格式非法：仍按数据安全错误失败，不得当作“待配置”跳过。

跳过结果携带空的广告、店铺和候选客户集合，避免生成不准确客户。

### 2. 工作流编排顺序

工作流取到并校验当前用户所属记录后，先调用现有 `SourcingService.runForWorkflow()` 启动1688寻源旁路。该方法自身维持非阻断行为，1688暂时不可用不会把客户发现工作流改成失败。

随后执行客户发现：

- `completed`：保持现有广告发现、店铺识别、线索清洗和评分流程。
- `skipped`：将 `ad_discovery`、`store_detection`、`lead_cleaning`、`lead_scoring` 标记为 `skipped`，在 `output` 中保存：

```json
{
  "reasonCode": "public_image_not_configured",
  "reason": "Public image URL is not configured; customer discovery was skipped."
}
```

主工作流执行任务正常结束，工作流状态为 `completed`、进度为100、线索数为0，不进入通用失败重试。

重新执行历史失败工作流时，仍走相同判断：配置已补齐则执行客户发现，仍为本机模式则明确跳过。

### 3. API状态

工作流响应和1688寻源汇总响应增加只读的客户发现状态，不新增数据库字段：

```ts
type CustomerDiscoveryStatus =
  | 'not_started'
  | 'running'
  | 'completed'
  | 'pending_public_image'
  | 'failed'
```

状态由 `ad_discovery`、`store_detection` 步骤及其 `output.reasonCode` 计算。列表读取时批量查询当前页工作流的相关步骤，禁止逐条查询造成 N+1。

1688寻源汇总接口复用同一状态计算规则，因此前端可以把真实寻源状态与客户发现状态组合显示。

### 4. 历史失败信息

旧记录中包含 `PUBLIC_ASSET_BASE_URL`、`only available locally` 或 `publicly reachable` 的错误，失败来源映射为 `customer_discovery`，不再返回空来源。前端显示“客户发现图片配置”，不再显示“失败环节：未知”。

真正的 PipiAds、Google Lens、Google Search 异常仍沿用现有供应商分类与重试规则。

## 前端设计

### 工作流列表

- `pending_public_image` 使用非失败的琥珀色提示“客户发现待配置公网图片”。
- 工作流状态保持“完成”，不展示失败详情或不可达图片错误。
- 历史失败记录的来源使用国际化标签，不直接展示内部枚举值。

### 1688寻源页

在现有“独立采购证据”提示下增加双模式状态提示：

- 寻源完成 + 客户发现待配置：显示“1688寻源完成，客户发现待配置”。
- 寻源中 + 客户发现待配置：显示“1688寻源中，客户发现待配置”。
- 寻源失败 + 客户发现待配置：显示“1688寻源失败，客户发现待配置”，并保留现有寻源失败详情与重试入口。
- 客户发现正常执行或已完成：不显示该提示，保持现有页面布局。

中英文文案同时维护，不增加新的页面或导航。

## 错误处理与安全边界

- “缺少公网图片”是可预期配置状态，不抛异常、不重试第三方客户发现。
- 图片资产归属异常、路径穿越或数据损坏仍抛错并使工作流失败。
- PipiAds、Google Lens 的真实超时、额度不足或第三方故障继续进入现有失败分类。
- 1688图片寻源继续使用本机受控文件字节上传后取得 `imageId`；不得把本机 URL 或 `imageAddress` 直接传给1688图片搜索。
- 不增加从1688标题推导关键词的降级逻辑。

## 测试与验收

### 后端

- 本机图片且无公开基址时，PipiAds、Google Lens 适配器均不调用。
- 同一场景下1688寻源启动方法被调用一次。
- 客户发现四个步骤记录为 `skipped`，原因码正确，工作流最终为 `completed`。
- 配置公开基址后仍调用两个客户发现适配器，并使用拼接后的公开图片 URL。
- 非法或越权资产路径仍导致失败。
- 历史本机图片错误映射为 `customer_discovery`，不再是未知来源。
- 工作流列表批量状态查询不产生 N+1。

### 前端

- 寻源完成且客户发现待配置时显示指定文案。
- 寻源运行中、失败时显示对应组合文案。
- 工作流列表显示待配置提示但不显示失败按钮。
- 历史失败详情显示“客户发现图片配置”，不显示“未知”。
- 现有关键词模式、公开图片模式、分页与重新寻源测试继续通过。

## 影响范围

- 后端：发现服务返回类型、工作流编排、工作流/寻源响应映射。
- 前端：工作流与寻源接口类型、列表提示、寻源状态提示及国际化文案。
- 数据库：不新增字段、不执行迁移；复用工作流步骤状态和 JSON 输出。
- 1688搜索、缓存、分页、供应商名称逻辑不修改。
