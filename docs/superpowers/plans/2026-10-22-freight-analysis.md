# 物流运费分析：设计与实施计划

用户已明确要求直接实现及更新文档。本次沿用现有 Dashboard / 工作台 / FOP provider 结构，不修改 FOP 生产库。

## 口径与交互

- 实际运费来自已审核发运单的 `hzkj_actual_freight`，以 `hzkj_actual_freight_time`（确认时间，非银行付款时间）按 UTC+8 归期。未确认、未审核或零费用不计入；不采用客户收费或物流预估价。
- 发运单 ID 是当前快照唯一粒度；同一履约订单多次发运可有多条成本。禁止重复发运单 ID。首次同步之后的调价、退款、重派尚需 FOP 新增明细/版本机制，不能声称已支持完整结算账本。
- 金额默认 USD；保留原币、原额、明确的原币到 USD 汇率、汇率日期和来源。不得把所有物流商原币默认当 CNY，不得无汇率静默混加。
- 固定合计、云途YT、4PX、万邦WB、燕文YW、极速JS、其他并列柱状。月份为所选年到当前月（历史年全12月）；周为锚点所在周加前三周、周一开始；年为所选年及前四年（最早2020）。当前未结束周期醒目标记，不伪装成已结期。
- 环比用当前期减完整上一期，同时给出百分比；上一期为0且本期非0时比例为空，显示“上期为0”，不构造无穷百分比。跨年基期也查询。
- 明细默认倒序，统计表列宽固定；环比开启展开统计表，关闭不收起。图表只允许拖动滑块调整横轴。单物流商趋势为居中弹窗。发运单明细进入当前可访问岗位工作台，分页合计为全筛选结果。

## 实施边界与步骤

1. 核实 FOP 源字段、币种、同步及权限，记录源码证据与人工待核项。
2. 新增 `fop-freight.types.ts`、`fop-freight.dto.ts`、`fop-freight.ts`：严格归一化、周期、环比、筛选和分页；单测先覆盖 UTC+8 跨月跨年、零基期、原币折算、合计与明细对账、错误数据拒绝。
3. 扩展 provider：独立 `allowedFreightIds` + `freight` analytics scope，缺失拒绝访问；在 FopDataService 校验 tenant、允许ID、业务权限和请求中途授权变化。演示提供独立实际运费样本，不用订单金额计算费用。新增两个 GET 接口 `/autoflow/integrations/fop/freight` 与 `/freight/details`，后者需要 workbenchRole。
4. 前端增加 Dashboard 运费模块、服务商趋势弹窗及工作台成本明细页；加载失败/会话切换清空旧数据，过滤变化防响应乱序。
5. 更新 OpenAPI 3.1.1 到字段级，更新来源诊断、需求、后续待办及人工核查清单、README；复用 HyperZone HTML 规范重建 MD/HTML。
6. 运行针对性与全量单测、API权限测试、类型/构建、真实本地HTTP契约验证及浏览器验收；记录结果后提交 Git 并推送。

## 重点审查

- 订单权限不能隐式获得物流成本权限；管理员也须独立 FOP 运费授权。
- 原币+汇率不能漏失或用人民币字段名推断；数值必须安全、有限、按分累加。
- 同期与上一期筛选相同，当前未结束周期与完整上期比较必须有说明。
- 确认时间不得改称实付时间；首次同步快照不得承诺覆盖后续调价。
- 总数不与各服务商二次叠加；明细筛选/分页总额与柱状图同口径。
